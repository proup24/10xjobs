# Matching (qualify) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After the processor finishes a job, decide it against every published profile (position, seniority, location, tech stack), storing qualified/rejected with every check and its reason in `job_matches`.

**Architecture:** A new `modules/matcher` mirrors `modules/processor`. `rules/` holds pure functions, one per criterion plus `decide`, that take the extraction document, the profile and a small vocabulary snapshot. `repositories/` holds raw SQL through `DatabaseService`, and `services/matcher.service.ts` matches one job. A new `match` BullMQ queue (`infrastructure/jobs/steps/match`) gets a nudge from the process step and a 60 s sweep that finds missing or stale rows. A newly published profile is backfilled by that same sweep, with no change to the API's publish path.

**Tech Stack:** NestJS, BullMQ, Prisma Next (`@prisma/orm-postgres`, raw SQL builder as in `processor.repository.ts`), Supabase Postgres + RLS, Vitest, zod.

**Spec:** `docs/superpowers/specs/2026-11-08-matching-design.md`

## Global Constraints

- Every check outcome is one of `pass` | `fail` | `unknown`. An `unknown` never rejects on its own.
- `rejected` when at least one check is `fail`, `qualified` otherwise. `unverified = qualified && (any unknown || extraction.needsReview)`.
- Seniority codes: `junior`, `mid`, `senior`, `staff`, `lead`, `principal`, `unstated`. Arrangement codes: `remote`, `hybrid`, `onsite`, `unstated`.
- Years-fallback margin `2`. Minimum stack score `0.4`. Backfill window `30` days. These live in `modules/matcher/config/matcher.config.ts` as constants, and changing any of them requires bumping `MATCHER_VERSION` _(plan call: the processor's `thresholds.ts` sets the same precedent; env vars would let a value change without a version bump)_.
- `MATCHER_VERSION = 1`, bumped on any rule or threshold change.
- Matchable job: in the processor's scope (active, `kind='job'`, has a LinkedIn job board source); `processingStatus='processed'`, not `closed`, `lastSeenAt >= now() - 30 days`; its current extraction has `schemaVersion = 2`.
- Profile offsets are in **minutes**, extraction offsets in **hours**.
- `job_matches`: users can only SELECT their own rows, and only the engine writes. `contract.prisma` is the only schema source.
- No LLM calls. Matching needs no `OPENROUTER_API_KEY`.

## Review Focus

1. **A job with several openings where only one fits** (for example, onsite in Paris or remote in the US, for a profile that wants remote worldwide) must pass on the fitting opening. It's tested in Task 3 (`best opening wins`).
2. **A region against another region** (a job in `EU`, a profile in `EMEA`) must overlap through shared countries, not by exact code only. Otherwise right jobs are missed. It's tested in Task 3.
3. **A tech stack made only of `null` codes, or only `nice` requirements,** must give `unknown` with score `null`, not `fail` with 0. It's tested in Task 4.
4. **A re-decision with the same outcome** must not move `decidedAt`, or the "new since you last looked" list fills with old jobs after every rematch. It's tested in Task 6.
5. **A job that's merged after being matched** must lose its rows on the next sweep, so the user never sees one posting twice. It's tested in Task 6 (`deleteInactive`).

### Task 3: Location rule

**Files:**

- Create: `rules/places.ts`, `rules/places.spec.ts`, `rules/location.ts`, `rules/location.spec.ts`.

**Interfaces:**

- Consumes: `MatchProfile`, `Check`, `bestOutcome` (Task 2); `Opening`, `Place as JobPlace` from `src/modules/processor/schema`; `Place as ProfilePlace` from `src/modules/users/types/place.types`.
- Produces:

```ts
export interface PlaceIndex {
  /** region code -> its country codes (region_countries). */
  countriesOfRegion: Map<string, Set<string>>;
  /** city id -> country code (cities). */
  countryOfCity: Map<string, string>;
}
export type Overlap = 'yes' | 'maybe' | 'no';
export function overlaps(job: JobPlace, profile: ProfilePlace, idx: PlaceIndex): Overlap;
export function checkLocation(openings: Opening[], profile: MatchProfile, idx: PlaceIndex): Check;
```

`overlaps` rules (in order):

1. Either side is `worldwide`: `yes`.
2. Resolve each side to a country set. For a region, that's its countries; for a country, itself; for a city, its country. A job city uses `cityId` → `countryOfCity`, and `countryCode` when `cityId` is null.
3. City against city: `yes` only when both ids are equal and non-null. A job city with a null `cityId` in the same country gives `maybe`. Otherwise `no`.
4. A job city with a null `cityId`: when its country set intersects the profile side, `maybe`, never `yes`. When it has no `countryCode`, `maybe`.
5. A region code with no countries in the index: `maybe`.
6. Otherwise, the country sets intersect: `yes`; they don't: `no`. Region against region shares countries this way.

`checkLocation`, per opening:

1. Kept arrangements are the opening's arrangements, with `unstated` expanded to all three, filtered to those whose profile list is non-empty. If none are kept: `fail`.
2. For each kept arrangement:
   - If the opening has no places: `unknown`.
   - Else, some `yes` over (job place × profile place) gives `pass`. Otherwise some `maybe` gives `unknown`. Otherwise strictness `mention` gives `unknown`, and `limit`/`label` gives `fail`.
   - Then, for `remote` only: when `timezones` is non-empty and none satisfies `tz.fromUtc <= profile.timezoneMax/60 && tz.toUtc >= profile.timezoneMin/60`, that arrangement becomes `fail`.
3. The opening's result is the best over its kept arrangements. If the opening's only arrangement was `unstated`, a `pass` is capped to `unknown`.
4. The check is the best over all openings. `detail` lists each opening's arrangements, places, deciding arrangement and outcome.

### Task 4: Tech stack rule

**Files:**

- Create: `rules/stack.ts`, `rules/stack.spec.ts`.

**Interfaces:**

- Consumes: `TechStack` from `src/modules/processor/schema`; `MatchSkill`, `Check` (Task 2); `MIN_STACK_SCORE`.
- Produces:

```ts
/** tech tag code -> codes it implies (tech_tags.implies). */
export type ImpliesMap = Map<string, string[]>;
export function checkStack(stack: TechStack | null, skills: MatchSkill[], implies: ImpliesMap): { check: Check; score: number | null };
```

The algorithm:

1. **Mastery by code.** Each skill gives `technology → mastery`, and also each code in `implies.get(technology)` at the same mastery. Keep the maximum per code.
2. **Units.** An ungrouped requirement is its own unit. Requirements sharing `group` form one unit, with `min` from `stack.groups` (1 if the group isn't listed). The unit's kind is the strongest member kind (`main` > `must` > `nice`), and its importance is the highest member importance.
3. **Comparable.** A unit is comparable when at least one member has a non-null `code`. Members with a null code go to `detail.notComparable`.
4. **Covered.** A unit is covered when at least `min` of its members have a code in the mastery map. Its mastery is the best mastery among covered members.
5. **Scored units** are the comparable units of kind `main` or `must`. If there are none: `unknown`, score `null`.
6. **Score** = `Σ importance × (covered ? mastery/10 : 0) / Σ importance`, rounded to 3 decimals.
7. **Outcome.**
   - There are comparable `main` units and none of them is covered: `fail`, and the reason lists the main codes.
   - Otherwise, a score below `MIN_STACK_SCORE` gives `fail`, listing the uncovered codes.
   - Otherwise: `pass`.
8. **Detail** holds `{ covered, uncovered, niceCovered, notComparable, score }`.

```sql
INSERT INTO job_matches (... , "decidedAt") VALUES (..., now())

  "extractionId" = EXCLUDED."extractionId", "matcherVersion" = EXCLUDED."matcherVersion",
  outcome = EXCLUDED.outcome, unverified = EXCLUDED.unverified,
  "stackScore" = EXCLUDED."stackScore", checks = EXCLUDED.checks, "updatedAt" = now(),
  "decidedAt" = CASE WHEN job_matches.outcome = EXCLUDED.outcome
```
